# ADR 0013: Undo for reversible actions

**Status:** Proposed — needs review by the Real-Time Architecture owner · **Amends:** `docs/adr/0001-event-model.md` (open question 1, undo semantics), `docs/adr/0011-attack-rulings.md` (undoing applied damage)
**Owner:** Real-Time Architecture (Raymond) · **Changes:** `openspec/changes/undo-reversible-actions` · **Ticket:** KAN-41 (FR-REC-02, FR-REC-03)

## Context

A GM who moves the wrong token, reveals a monster too early, clears the wrong condition, rules a miss as a hit or applies damage to the wrong target has to rebuild the change by hand. Every event already carries the value it replaced (invariant 6), so undo can be a compensating event (ADR 0001). Three things were missing:

- **Grouping.** One command can commit several events. `token.configure` (the token editor save) can emit a hide, a move and a condition change in one batch, hide first and reveal last. `roll.applyDamage` emits a `TokenStatsSet` and a `RollDamageApplied`, and ADR 0011 notes that undo must reverse them as one unit. Nothing in `CommittedEvent` recorded which events belonged to one command.
- **Somewhere `decide` can see recent actions.** `decide` is pure and sees only `RoomState`.
- **A rule for concurrent edits.** ADR 0001 open question 1 asks what undo does when later events touched the same thing.

## Decision

### Undo semantics

Only the GM can undo. The GM picks the action from the activity log, and undo reverses exactly that action, whoever performed it. It does not have to be the latest. There is no redo, no top-bar button and no keyboard shortcut: a blind "undo the latest" hides what is being reversed, and in a shared room the latest action is often someone else's. A player's `history.undo` is refused as `forbidden`.

The reversible events are `TokenMoved`, `TokenHiddenSet`, `TokenConditionsSet`, `RollRuled`, `RollDamageApplied`, and `TokenStatsSet` **only inside an Apply**. A command is undoable only when **every** event it produced is reversible. A manual HP/AC edit is not undoable, because the GM just edits it again. Dice rolls are not undoable, so a result can't be rerolled away. Undoing one action never needs other actions undone first.

### `commandId` on `CommittedEvent`

`LiveRoom.commit` generates one `randomUUID` per committed batch and stores it on every event of the batch: `CommittedEvent.commandId` (optional), `NewEvent.commandId`, and a nullable Postgres column `events.command_id` (migration `0005_event_command_id`). It is pipeline metadata, like `seq` and `at`, so `decide` never sees it. System batches get one too.

Events committed before this change have no `commandId`. `eventMeta` keys them as `seq:<seq>` and marks them `legacy`, and they are **never undoable**. Their batch boundaries are unknown, so undoing one event could split an old Apply: the roll would read un-applied while HP stayed lowered, and a second apply would deal the damage twice. No backfill is needed.

`commandId` is unrelated to the client's `clientCommandId`, which only matches acks to requests.

### Undo history in `RoomState`, built by `reduce`

`RoomState.undo` holds recent actions, oldest first: `{ commandId, actorId, undoable, events, tokenNames, rollLabels }`. The label maps keep token names and "Aria → Goblin" roll labels from the time of the action. `reduce(state, event, meta?)` takes optional `{ commandId, actorId }`, and `reduceCommitted(state, committed)` supplies it. The server (load and commit), the activity log replay and the GM's web client all use it. Without `meta`, `reduce` behaves as before and leaves the history alone.

Batches are contiguous, so an event either extends the last entry (same `commandId`) or starts a new one. The entry is created on a batch's first event, and any non-reversible event marks it `undoable: false`, in whatever order the batch's events come. Whether the whole action can be undone (`canUndo`) is decided once it is complete: a `TokenStatsSet` needs a `RollDamageApplied` beside it. A closed entry that can't be undone is dropped when the next batch starts. At that moment, and only then, the history is trimmed to the newest 20 closed entries (`UNDO_HISTORY_LIMIT`). An undo's own inverse events open an entry that its `ActionUndone` removes again, so trimming while an entry is open would evict an unrelated action. The history is derived state, and a replay of the log rebuilds it, so it survives a restart without snapshots.

### `history.undo { commandId }` emits inverses plus `ActionUndone`

`decide` finds the named entry. If it is not in the history or can't be undone, it rejects as `invalid` with "That action can no longer be undone." It then checks that the current state still matches every value the action set:

- **Token events:** the token exists and still has the position, hidden flag, conditions (compared as a set) or stats the action gave it.
- **Roll events:** the roll is still in the 30-roll window, with the ruling the action gave it, or still Applied.

On a mismatch it rejects with a message naming the token or roll, for example "Can't undo: Goblin has changed since.", and nothing is appended. The action stays undoable if the state matches again later.

Otherwise it emits the inverse of each event **in reverse order**, then `ActionUndone { commandId }`. Most inverses are the same event type with the value and `previous` exchanged, so they reuse existing `reduce` branches and visibility filters. Reverse order keeps `token.configure`'s "hide first, reveal last" rule when undoing.

`RollDamageApplied` carries no `previous`, because it always replaces `false` (ADR 0011). Its inverse is a new event, `RollDamageUnapplied { rollId, amount }`, which clears the mark. Undoing an Apply emits `[RollDamageUnapplied, TokenStatsSet (HP back), ActionUndone]`, and the roll can be applied again afterwards.

`reduce` for `ActionUndone` removes the undone entry, and the entry opened by the undo's own inverse events, so an undo is never itself undoable. `ActionUndone` carries only the id. The activity log formats it from the entry, which is still in the history of the state just before it: "Raymond undid the move of Goblin". It replaces no stored value, so invariant 6 holds.

### Visibility

- Players get `undo: []` in every snapshot.
- `ActionUndone` is always redacted for players. They have no activity log, and the inverse events already delivered whatever they may see.
- `RollDamageUnapplied` is filtered exactly like `RollDamageApplied`: redacted for a GM-only roll or a hidden target.
- `commandId` is stripped from every event sent to players. An id shared between a visible event and a redacted one would tell a player that a hidden change was part of the same editor save. Player clients therefore keep no history.

### Activity log

For each action, the GM's activity log puts an Undo button on its newest entry when the GM client's history says it can still be undone, labelled from the entry ("Undo move Goblin"). It marks an action Undone when its `ActionUndone` is on the page, and it shows a refusal message on the entry that was clicked.

### Widening the reversible set

1. Add the event type to `REVERSIBLE_EVENT_TYPES` in `packages/shared/src/undo.ts`.
2. Add its inverse in `inverseOf`, its current-value check in `undoConflict`, and a phrase in `describeUndo`. If it should only be undoable next to another event, say so in `canUndo`.
3. Check that its inverse passes through the visibility filters safely. An event with no `previous` needs a dedicated inverse event, as `RollDamageApplied` did.

## Consequences

- **Contract change.** `CommittedEvent`, `DomainEvent` (`ActionUndone`, `RollDamageUnapplied`), `Command` (`history.undo`), `RoomState` and `reduce` change. All additions are optional or defaulted, and existing logs replay unchanged.
- **Deploy web and server together.** An older reducer's `assertNever` throws on the new events, as with every earlier event addition.
- **Rollback.** The nullable column can stay. Rolling the code back after undo has been used would leave `ActionUndone` and `RollDamageUnapplied` rows that an older reducer cannot read. Those rooms would need the rows handled by hand.
- **Edits to other fields do not block.** Renaming a token after moving it leaves the move undoable, because the position is still exactly what the move set.
- **Only recent rolls.** A ruling or Apply whose roll has left the 30-roll window can no longer be undone, matching ADR 0011's rule that only recent rolls can be ruled.
- **Not covered.** Checkpoints, redo, player undo, HP/AC edits on their own, dice rolls, and every event type outside the reversible set.

## Alternatives considered

- **Undo the latest action only (Ctrl+Z style).** Rejected after trying it: the GM could not see what a press would reverse, and could not get past a refused action to an older one.
- **Undo per event.** Rejected. An editor save or an Apply would take several undos and could be left half undone.
- **Group in `LiveRoom` memory only.** Rejected. The grouping would be gone after a restart.
- **A marker event after each undoable batch.** Rejected. It doubles the log, and a player-visible marker next to a redacted event reveals a hidden change.
- **One composite `ActionUndone { reverted }` inverted by `reduce`.** Rejected. It would need its own copy of every visibility rule for the reversible events.
- **Force the old value even if the state has changed.** Rejected. It would silently overwrite a newer change made by someone else.
